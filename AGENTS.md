# AGENTS.md — Инструкции для ИИ-агента (agent instructions)

> Базовый файл инструкций для работы ИИ-ассистента над пакетом
> **`game-overrule-shared`**.

## 1. Цель

Пакет — единый источник доменных типов, чистых игровых правил, протокола и
wire-контракта для Overrule. Его используют два независимых потребителя:

- клиент [`game-overrule`](https://github.com/7ka-dev/game-overrule);
- сервер [`time2join.me-colyseus`](https://github.com/7ka-dev/time2join.me-colyseus)
  (`src/games/overrule`).

Документ задаёт правила работы агента: как думать, планировать, менять код,
проверять результат и фиксировать решения.

## 2. Общие принципы работы

- **Итеративность**: маленькие шаги → проверка → следующий шаг
- **Без разрушения**: не удаляй и не переписывай без обоснования существующий
  непустой код, если он не конфликтует с текущей задачей
- **Исследование**: всегда читай релевантные файлы и использования в клиенте и
  сервере перед изменениями
- **Консистентность**: стиль, структура, нейминг и паттерны пакета
- **Явность и простота**: KISS, меньше магии
- **Единственный источник правды**: типы и правила живут здесь, а не
  дублируются в клиенте или сервере
- **Чистота**: никакого IO, DOM, Node-инфраструктуры и Colyseus
- **Обратная совместимость**: пакет — публичный контракт для двух репозиториев;
  удаление/переименование экспорта считается breaking change
- **ADR-first**: значимые решения по контракту и совместимости фиксируй в ADR
  (см. §6)

## 3. Процесс работы

1. **Понимание** — прочитай задачу, уточни неясности (минимально необходимые
   вопросы)
2. **Планирование** — предложи короткий план действий (списком) **перед**
   началом правок
3. **Исследование** — изучи `src/`, `README.md`, а также места использования
   в клиенте и сервере
4. **Реализация** — внеси изменения минимальным, фокусным диффом
5. **Проверка** — `npm run typecheck` и `npm run build`; при изменении `core`
   прогони тесты потребителей (см. §7)
6. **Ревью** — после решения отдай результат на ревью. После ревью пользователь
   сам сделает коммит или попросит сделать тебя
7. **Фиксация** — кратко опиши изменения; при необходимости обнови README и
   пересобери `dist/`

### 3.1 Правила работы с git (жёсткие)

- **Не коммитить без явной команды пользователя.** Команда вида «коммить и
  продолжай» авторизует коммит **только текущей завершённой задачи**, а не все
  последующие.
- Пока ревью не пройдено — изменения остаются в рабочем дереве (при
  необходимости staged), но **не попадают в историю**.
- `dist/` — часть пакета: он закоммичен, потому что потребители ставят пакет
  напрямую из GitHub. Перед коммитом **всегда** запускай `npm run build`, чтобы
  `dist/` соответствовал `src/`.
- **Никогда не редактируй `dist/` вручную** — только через сборку.
- Перед коммитом проверь `git status`: в индекс должны попасть и `src/`, и
  обновлённый `dist/`.
- Не коммить сломанный код: `typecheck` и `build` должны проходить.
- Коммит-сообщения — на английском, коротко и по существу.
- Если изменение ломает API, предупреди пользователя и перечисли, что нужно
  обновить в клиенте и на сервере (их lock-файлы указывают на конкретный commit).

## 4. Стиль кода (TypeScript)

- TypeScript: строгий режим (`strict: true`)
- Без `any` без веской обоснованной причины
- Имена: `camelCase` — переменные/функции, `PascalCase` — типы/интерфейсы,
  `UPPER_SNAKE_CASE` — константы
- **Комментарии — на английском** (документация репозитория — на русском)
- Комментарии — только по смыслу («почему», а не «что»); избыточные не добавляй
- Предпочитай чистые функции и `readonly`-параметры; не мутируй входные данные
- Минимум зависимостей: runtime-зависимостей у пакета быть не должно
- Относительные импорты — с расширением `.js` (пакет собирается в ESM и CJS)
- Публичные функции и интерфейсы — с явными типами; экспортируй только то, что
  действительно является контрактом

## 5. Архитектурные границы

| Путь | Назначение | Ограничения |
|---|---|---|
| `src/types` | Доменные типы (dice, category, phase, card, player, game, event) | Без IO и внешних зависимостей; допустимы тривиальные чистые хелперы |
| `src/core` | Чистые правила: scoring, deck, dice, freeze, rules, turn, events | Без Colyseus, UI, сервера, клиента, IO |
| `src/protocol` | `ClientToServer` / `ServerToClient` | Только типы сообщений |
| `src/utils` | Чистые утилиты (shuffle) | Без IO и внешних зависимостей |
| `src/wire.ts` | `GameStateWire` и имена комнат | Только структура данных, без schema-классов |

Запрещено:

- импортировать `@colyseus/*`, `express`, `react`, `phaser`, `node:*`, `fs`,
  `process`, глобальные объекты DOM;
- добавлять schema-классы (`Schema`, `@type`, `schema()`, `t.*`) — shared не
  должен зависеть от Colyseus, поэтому wire-контракт остаётся plain TypeScript;
- импортировать код из репозиториев клиента или сервера;
- хранить в пакете игровое состояние, таймеры, сетевые подключения или UI-логику.

Потребители:

- клиент: `@colyseus/sdk` **0.17.43**, schema **4** (транзитивно) — использует
  `GameStateWire` как тип состояния;
- сервер: Colyseus **0.17.x**, schema **4** — держит schema-классы локально и
  проверяет их на соответствие `GameStateWire` при сборке.

При изменении `wire.ts` проверь оба потребителя: форма полей должна совпадать с
серверной схемой и с `toView()` в клиенте.

## 6. Работа с документацией

- `AGENTS.md` — главный документ инструкций агента
- `README.md` — публичное описание пакета, структуры, сборки и API
- При изменении публичного API обнови `README.md`
- Значимые решения по контракту/совместимости фиксируй в ADR репозитория
  клиента (`game-overrule/docs/adr`), потому что они затрагивают оба
  потребителя; в README добавь ссылку на соответствующее решение
- Отдельного `tasks/` в этом репозитории нет: задача и ревью ведутся в диалоге
  или issue
- Не дублируй в README тексты карт и правила, которые уже описаны в
  `src/core/deck.ts` и `CARDS.md` клиента

## 7. Тестирование и качество

- Обязательный минимум перед ревью/коммитом:
  - `npm run typecheck`
  - `npm run build` (обновляет `dist/`)
- При изменении `src/core` прогони тесты ядра в клиенте:
  - в `game-overrule`: `npm test` (каталог `tests/shared`)
- При изменении `src/wire.ts` или `src/protocol` проверь сборку сервера:
  - в `time2join.me-colyseus`: `npx tsc --noEmit`
  - при возможности — `npx mocha -r tsx "test/overrule/*_test.ts" --exit`
- Новую чистую логику покрывай тестами. Если тест зависит от `CARDS.md`
  клиента, он остаётся в клиенте; остальные тесты пакета можно добавлять сюда
- Не коммить сломанный код; архитектурные границы проверяются при ревью

## 8. Коммуникация

- Отвечай кратко, структурно, с обоснованием ключевых решений
- Файловые пути указывай относительно корня пакета
- **Ревью-цикл:** после решения отдавай результат на ревью. Пользователь сам
  сделает коммит или попросит сделать тебя. **Сам инициировать коммит без
  команды нельзя** (см. §3.1)
- Если для изменения нужен новый commit shared-пакета в клиенте/сервере,
  явно скажи, что их lock-файлы нужно обновить
